# wjs-themes Django 5.2 Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the `wjs-themes` package (two Janeway themes, `JCOM-theme` and `wjs-bootstrap`, plus an `advanced_admin` app) work correctly under Django 5.2, and release a version downstream `wjs-*` repos can pin against.

**Architecture:** No structural changes — this is a compatibility pass over an existing, small package (6 non-trivial `.py` files, 173 templates). Verification is done by installing the package editable into the already-migrated `janeway-5.2` checkout and exercising it live, per this repo's own documented convention (no automated test suite exists or is added).

**Tech Stack:** Python 3.11+, Django 5.2, `django-bootstrap5`, `django-upgrade`, `ruff`, `djlint`.

**Spec:** `docs/superpowers/specs/2026-08-26-django-5.2-migration-design.md` (this repo).

## Global Constraints

- Python floor: `>= 3.11` (confirmed for all five `wjs-*` repos in this migration effort).
- Django target: `5.2` (matching `janeway-5.2`'s `Django~=5.2.17`).
- `django-bootstrap5 >= 26.2` (verified installed and working in the `janeway-5.2` venv).
- No behavioral change to rendered themes.
- No automated test suite is added — verification is manual/live, per `.claude/rules/tests.md`.
- Package version bumps to `2.1.0` so downstream repos (`wjs-submission-project`'s
  `wjs-themes >= 2.0.18`) can pin against a known-compatible release.

### Task 6: Fix the removed `length_is` template filter

**Added after Task 5's live verification found a real Django 5.2 incompatibility that Tasks 1–4's
Python-file-focused tooling and the narrower template-pattern grep both missed:** `length_is` was
removed in Django 5.1 (correction: an earlier version of this task said 5.0 — verified against
installed package metadata: present in 4.2.30 and 5.0rc1, absent in 5.2.17). It's used identically
in both themes' article-listing partial, and caused
500 errors on the homepage and issue pages (article pages and the manager dashboard were
unaffected — they don't render this partial).

**Files:**
- Modify: `wjs/themes/JCOM-theme/templates/elements/article_listing.html:11`
- Modify: `wjs/themes/wjs-bootstrap/templates/journal/components/article_listing.html:11`

**Interfaces:** None — template-only fix, no Python interface changes.

- [ ] **Step 1: Apply the fix to both files**

Both files have the identical line:

```django
{% if not request.available_languages|length_is:"1" %}
```

Change to:

```django
{% if request.available_languages|length != 1 %}
```

(`not X|length_is:"1"` and `X|length != 1` are equivalent: both mean "the list's length is not
exactly 1". This is Django's documented replacement pattern for `length_is`.)

- [ ] **Step 2: Verify**

```bash
grep -rn "length_is" wjs/themes/
```

Expected: no output.

- [ ] **Step 3: Commit**

```bash
git add wjs/themes/JCOM-theme/templates/elements/article_listing.html \
        wjs/themes/wjs-bootstrap/templates/journal/components/article_listing.html
git commit -m "fix: replace removed length_is template filter

Django 5.0 removed the length_is template filter. Both themes used
it identically in article_listing.html to decide whether to show a
language badge (only when more than one language is available).
Replaced with the documented equivalent: length != 1. Found by
Task 5's live verification -- caused 500 errors on the homepage and
issue pages under both themes."
```

- [ ] **Step 4: Re-run the live verification pages that were affected**

Per Task 5's Steps 4–5, re-check (with this fix installed into `janeway-5.2`) the homepage and an

### Task 7: Fix the `admin.E109` regression in `ArticleAdmin.list_display`

**Added after the final whole-branch review found Task 5's `manage.py check` failure had been
misdiagnosed as pre-existing.** It is a genuine Django 5.x regression, confirmed by side-by-side
reproduction against real Django 4.2.30 and 5.2.17 installs: `wjs/advanced_admin/admin.py`'s
`ArticleAdmin.list_display` includes the string `"identifier"`. `identifiers.Identifier.article`
(in `janeway-5.2/src/identifiers/models.py`) is a `ForeignKey` to `submission.Article` with no
`related_name`, so its reverse query name defaults to `identifier` — colliding with `Article`'s
own `identifier` property. Django 5.x's `_check_list_display_item` admin check was tightened to
also flag reverse-FK query names (previously it only flagged `ManyToManyField`), so this
now raises `admin.E109`, a `checks.Error` that aborts every management command (`migrate`,
`collectstatic`, this package's own `install_themes`) under Django 5.2 unless `--skip-checks` is
passed — a real deployment blocker anywhere `wjs.advanced_admin` is installed (it's listed in
`wjs-profile-project`'s `INSTALLED_APPS`).

**Files:**
- Modify: `wjs/advanced_admin/admin.py` (the `ArticleAdmin` class, around the `list_display` line)

**Interfaces:** None — internal `ModelAdmin` change; no change to what the admin UI shows.

- [ ] **Step 1: Add a display method and update `list_display`**

Current:

```python
    list_display = ["title", "pubid", "journal", "state", "identifier"]
```

Change to (add the method anywhere in the class body, and update the `list_display` line to
reference it by name instead of the raw field/property name):

```python
    list_display = ["title", "pubid", "journal", "state", "identifier_display"]
```

```python
    @admin.display(description="identifier")
    def identifier_display(self, obj):
        """Return the article's identifier for the admin list display.

        Not named "identifier" directly: identifiers.Identifier.article has no related_name,
        so its reverse query name is also "identifier", which Django 5.x's admin.E109 check
        now flags when a list_display item resolves to a reverse FK relation instead of a
        plain attribute. Renaming this display method sidesteps the field lookup entirely.
        """
        return obj.identifier
```

Place the method near the other display-style methods already in this class (e.g. near
`get_list_filter`), matching the class's existing style.

- [ ] **Step 2: Verify with `manage.py check` — WITHOUT `--skip-checks`**

```bash
cd /home/yakky/Projects/projects/sissa-1.8/janeway-5.2/src
pyenv activate janeway-5.2
python manage.py check
```

Expected: no `admin.E109` (or any other) error. This directly satisfies the spec's Verification
step 5, which Task 5 could only pass with `--skip-checks` before this fix.

- [ ] **Step 3: Commit**

```bash
git add wjs/advanced_admin/admin.py
git commit -m "fix: resolve admin.E109 on ArticleAdmin.list_display

Django 5.x's admin.E109 check was tightened to also flag list_display
items that resolve to a reverse foreign-key relation, not just
many-to-many fields. identifiers.Identifier.article has no
related_name, so its reverse query name defaults to 'identifier',
colliding with Article's own identifier property -- and Article was
already in ArticleAdmin.list_display under that name. Renamed to a
display method (identifier_display) that isn't a field/relation name,
sidestepping the check. No change to what the admin UI shows.

Found by the final whole-branch review, which reproduced the check's
Django 4.2.30 vs 5.2.17 behavior side by side to confirm this is a
genuine 5.x regression, not pre-existing (Task 5 had misdiagnosed it
as such, using --skip-checks to work around it instead)."
```
