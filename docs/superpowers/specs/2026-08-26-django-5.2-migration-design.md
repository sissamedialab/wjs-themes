# wjs-themes: Django 5.2 Migration — Design

## Context

This is the first of five independent `wjs-*` plugin repos being ported to Django 5.2, following
the core `janeway-5.2` migration (Django 4.2.30 → 5.2.17, Python floor `>=3.9` → verified
`3.10`–`3.13`) on branch `migration/1.8-phase7-pep440-compat-release`.

The five repos and their dependency order (from each `setup.cfg`'s `install_requires`):

- **Leaves (no wjs-internal deps, portable independently):** `wjs-themes`, `wjs-search-user`,
  `wjs-utils-project`
- **`wjs-submission-project`**: depends on `wjs-themes >= 2.0.18` and `wjs-user-search >= 2.0.3`
- **`wjs-profile-project`**: depends on `wjs-themes`, `wjs-submission`, and `wjs_mgmt_cmds`
  (the package built by `wjs-utils-project`); also the only repo with an explicit `Django ~= 4.2`
  pin today

`wjs-themes` was chosen to go first: it is a leaf with the smallest Python surface, and both
`wjs-submission-project` and `wjs-profile-project` need it done before their own ports can proceed.
This spec covers `wjs-themes` only. Each of the other four repos gets its own
brainstorm → spec → plan → implementation cycle.

**Amendment (at planning time):** the Python floor across all five repos is now confirmed as
**3.11** (not the 3.10 floor assumed above, which was carried over from the core migration's own
verified range). This repo declared no `python_requires` at all, so this is a new addition rather
than a correction — see Changes.

## Goal

Make `wjs-themes` (package `wjs-themes`, repo `wjs/wjs-themes`) work correctly under Django 5.2,
with no behavioral change to the rendered themes, and release it as a version downstream repos can
pin against.

## Repo shape (as found)

- Distributed as a **standard Python package**, not a Janeway plugin (no
  `wjs/plugins/<name>/`-style layout) — installed editable into a Janeway checkout.
- Python surface is 6 non-trivial files:
  - `wjs/advanced_admin/admin.py`, `admin_site.py`, `urls.py` — import Django (`admin`, `forms`,
    `AdminSite`, `path`, `HttpRequest`)
  - `wjs/themes/apps.py` — imports Django (`AppConfig`, `settings`)
  - `wjs/themes/management/commands/install_themes.py` — imports Django (`apps`, `settings`,
    `BaseCommand`)
  - `wjs/themes/context_processors.py` — a context processor (Django integration point via its
    `request` parameter and registration in `TEMPLATES`), but its body imports nothing from
    Django — only `importlib.metadata.version`
  - (`wjs/themes/JCOM-theme/build_assets.py` and `wjs/themes/wjs-bootstrap/build_assets.py` are
    dev-only asset build scripts, not part of the installed package, and don't import Django;
    `__init__.py` files are empty)
- 173 templates across two themes (`JCOM-theme`, `wjs-bootstrap`), no `templatetags/` directory,
  no bare `{{ form }}` renders, no matches for other known Django-5.x-sensitive template patterns
  (`{% load staticfiles %}`, `{% ifequal %}`/`{% ifnotequal %}`, `{% now %}`, `DATETIME_FORMAT`).
- `setup.cfg` declares no explicit Django version at all (relies on the host app's pin) and one
  dependency, `django-bootstrap5`, currently unpinned.
- **No automated test suite** (documented in the repo's own `.claude/rules/tests.md`): no
  `tests/` directory, no pytest config or dependency. Verification is manual, inside a running
  Janeway checkout — this spec does not add a test suite.
- CI (`.gitlab-ci.yml`) runs only lint (`Pre-commit`, via an included template from
  `wjs/wjs-profile-project`) and package build/deploy on the `python:3.11` image — no job
  exercises this package's Python or template code.

## Approach

Use the same tool-assisted method as the core `janeway-5.2` migration: run `django-upgrade
--target 5.2` and `ruff` over the 5 Django-importing files to catch mechanical rewrites, then
manually read all 6 non-trivial files (small enough for a full read, and `context_processors.py`
is worth a manual look for its `request`-parameter signature even though it has no Django imports
to rewrite) for anything the tools can't catch — custom `AdminSite` registration, URL patterns,
`AppConfig` signature, management command API. Given the core repo's much larger, similarly-shaped
codebase came through `django-upgrade --target 5.2` with only a handful of manual follow-ups
(documented in its handover notes), expect this file set to need few or no changes.

Templates (173 files, no custom template tags) get a targeted grep sweep for known
Django-5.x-sensitive patterns rather than a full manual read of every file — proportionate to risk
given the sweep already run in this spec's research found nothing, and there's no custom template
tag code whose API could have broken.

Considered and rejected:
- **Manual-only review, no tooling**: slower for no accuracy benefit on a codebase this size where
  `django-upgrade` already proved reliable on the core repo.
- **Defer themes-specific verification to a downstream repo's test suite**: `wjs-submission-project`
  and `wjs-profile-project` have no working Django-5.2-compatible test run yet either (they're
  ported after this), so there's no such suite to lean on today, and it would leave this repo's own
  release unverified in isolation.

## Changes

1. **Python fixes** in the 6 files listed above, as found by `django-upgrade --target 5.2` +
   manual review. Scope is whatever those tools/review turn up — this spec does not predict
   specific line changes, since none are known to be needed yet.
2. **`setup.cfg`**:
   - Add `django-bootstrap5 >= 26.2` to `install_requires` (currently unpinned). `26.2` is the
     version already installed and verified working in the core `janeway-5.2` repo's Django 5.2
     venv, and its PyPI metadata declares `Framework :: Django :: 5.2` support.
   - Bump `version` from `2.0.19.dev1` to a release version (proposed: `2.1.0`) so
     `wjs-submission-project` (`wjs-themes >= 2.0.18`) and `wjs-profile-project` can pin against a
     known-Django-5.2-compatible release once this is tagged and uploaded via the existing
     `Upload package` CI job.
   - Add `python_requires = >= 3.11` (new addition — none was declared before; matches the
     confirmed floor for all five repos in this effort).
3. **`.gitlab-ci.yml`**: bump the `default.image` from `python:3.11` to `python:3.13`, matching
   the 3.10–3.13 Python floor the core repo's CI matrix (`.github/workflows/ci.yml`) verified.
   This image only runs lint/build/deploy, not a test matrix, so a single current version is
   sufficient.
4. No changes to SCSS/JS assets, `wjs-search-user`, `wjs-utils-project`, or any other repo.

## Verification

Per this repo's own documented convention (`.claude/rules/tests.md`), since there is no automated
test suite:

1. `pip install -e .` this package into the `janeway-5.2` checkout's virtualenv (already on
   Django 5.2.17).
2. From `janeway-5.2/src`, run `python manage.py install_themes` to symlink `wjs-bootstrap` and
   `JCOM-theme` into Janeway's `themes/` directory and apply `wjs/install/settings.json`.
3. Select each theme in turn as the "Journal Theme"
   (`http://<journal-domain>/manager/settings/journal/`) on a test journal.
4. Visually check: an article page, an issue page, and the backoffice dashboard, for each theme.
   Confirm no rendering errors and no unexpected markup/styling regressions.
5. Run `python manage.py check` against the janeway-5.2 project with the theme installed.
6. Run this repo's own `Pre-commit` lint job locally (or via CI) to confirm `ruff`/`djlint` still
   pass after the Python fixes.

No automated test suite is added, per repo convention — a future decision to add one is out of
scope for this port.

## Out of scope

- Porting `wjs-search-user`, `wjs-utils-project`, `wjs-submission-project`, or
  `wjs-profile-project` — each gets its own spec.
- Adding an automated test suite to `wjs-themes`.
- SCSS/JS asset changes.
- The two cross-cutting decisions flagged in the core migration's handover notes
  (`cms.SubmissionItem` uniqueness migration, `USE_L10N` removal) — those belong to the core
  `janeway-5.2` repo, not this one, and are unaffected by this port.
